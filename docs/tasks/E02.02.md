# E02.02 — Approvazione vincolata e receipt

Status: `VERIFIED_LOCAL_PARTIAL`

## Implemented

- `ActionApprovalService::request()` issues a one-shot Flow approval carrying
  only the ActionIntent digest, target digest, tenant/principal binding, and a
  unique execution identity. Proposed arguments are not persisted in the
  approval payload.
- The approval is bound to the tenant three ways, and all three must agree:
  the active `TenantContext` must equal the intent's tenant, the parent Flow
  run must belong to that tenant, and the persisted `flow_approvals.tenant_id`
  (stamped by the host from the ambient tenant) must equal the tenant in the
  payload on every `approve()` and `verifyForExecution()`. A mismatch at
  issuance throws `ActionApprovalException::contextMismatch()` and writes no
  approval row.
- `approve()` revalidates the current intent and ACL immediately before the
  atomic Flow token consume. Replay, expiry, digest changes, and an ACL denial
  return the same invalid-approval failure.
- `verifyForExecution()` re-reads the consumed approval and revalidates the
  expiry, digest, execution identity, and current ACL immediately before an
  effect. A revoked grant or a lapsed approval therefore denies without
  authorizing a write. Flow only expires rows that are still pending, so the
  expiry of an approved row is enforced by this method.
- The intent digest is computed over a structured, canonical JSON document
  (`ActionCanonicalizer`), not a delimiter-joined string, so a `|` inside a
  model-supplied field cannot shift into a neighbouring field and reproduce
  another intent's digest. The arguments are digested from `args` themselves;
  the public `argsDigest` constructor field is not trusted, so an intent
  rebuilt with changed arguments and the original digest is refused.
- Every denial that can be attributed to an approval row is appended to
  `flow_audit` as `action_approval.denied`, on that row's run and tenant, with a
  reason code (`binding_mismatch`, `acl_denied`, `replayed`, `not_pending`,
  `not_approved`, `expired`, `execution_mismatch`), the approval and execution
  identifiers, the bounded action and principal identifiers, and the attempted
  intent digest. The payload never holds the token, the arguments or free text
  from the proposal. A failed audit write propagates instead of being dropped.
- The underlying Flow approval consume remains the single-use race boundary.

## Remaining gaps

- No complete browser journey through the approval inbox was executed in this
  repository; the existing Flow admin surface remains the UI integration
  point.
- Flow/Rebel native step-up adapters and production PostgreSQL two-worker race
  evidence remain cross-package work.
- The service is not yet wired into every MCP/Flow executor; callers must use
  `verifyForExecution()` before the side effect. Nothing calls it today, so the
  change has no runtime effect until the E02.03 gateway adopts it.
- `verifyForExecution()` is a pure check: it does not record that the
  `execution_id` was spent, so within the approval window the same receipt
  verifies repeatedly. Exactly-once execution needs the gateway (E02.03) to
  reserve `execution_id` atomically under a database uniqueness constraint
  (SEC-AI-ACT-001, mutating actions, item 3). Until then no caller may treat a
  successful verification as permission to run an effect more than once.
- A token that Flow does not know has no run to attribute a denial to, so
  `approve()` refuses it without an audit row; the gateway sees that refusal as
  the exception and records it at its own choke point.
