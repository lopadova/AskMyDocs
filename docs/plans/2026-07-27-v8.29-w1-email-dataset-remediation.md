## Piano di implementazione

### 1. Introdurre un pool bounded di handle

`JsonlDatasetWriter` non deve mantenere aperti tutti gli shard fino a `finish()`.

Implementare un pool LRU o FIFO con limite conservativo, ad esempio 32 o 64
handle:

- primo accesso al path: apertura `xb` per preservare la garanzia no-overwrite;
- dopo eviction: riapertura `ab`;
- flush + close prima di rimuovere un handle dal pool;
- nessun momento con più di `MAX_OPEN_HANDLES`;
- dati e indice condividono lo stesso budget;
- `finish()` chiude ogni handle ancora aperto;
- `abort()` tenta di chiuderli tutti anche se uno fallisce, poi riporta
  l'elenco completo degli errori;
- nessuna eccezione deve lasciare handle vivi o pubblicare una directory
  parziale;
- conteggi e checksum devono restare byte-identici agli artefatti pubblicati.

Rendere il limite iniettabile nei test senza esporlo come opzione pubblica non
necessaria.

Test:

- pool con limite 2/4 e molti shard;
- eviction + reopen in append;
- errore di flush/close;
- abort dopo errore;
- generazione `gold`, `demo`, `large`, `stress`;
- `--check` contro gli hash documentati;
- esecuzione del profilo stress con `ulimit -n 256`.

Il test di regressione deve fallire sul codice vecchio con `Too many open
files` e passare dopo la modifica.

### 2. Guardrail ambiente per la delivery

Il comando si dichiara harness `local/testing`, quindi deve imporlo nel codice:

- dry-run, validate ed estimate-cost restano utilizzabili senza rete;
- APPEND e purge devono rifiutare ambienti diversi da `local`/`testing`;
- non affidarsi al fatto che le password production “dovrebbero” essere vuote;
- un eventuale override non deve essere un semplice env boolean permanente:
  richiede un percorso di conferma e audit esplicito.

Testare `production`, `staging`, `local`, `testing` e config cache.

### 3. Conferma DB-backed per purge

Ogni combinazione che elimina messaggi:

- `--purge-dataset`;
- `--purge-dataset --purge-only`;
- `--purge-all-seeded`;
- alias legacy `--purge`;

deve richiedere un token single-use persistito in DB e legato a:

- operazione esatta;
- dataset version;
- mailbox/project selection normalizzata;
- manifest checksum;
- actor;
- scadenza breve;
- hash canonico degli argomenti.

Implementare preview e consume con lo stesso schema di sicurezza di
`AdminCommandNonce`:

- salvare soltanto l'hash del token;
- `lockForUpdate` durante il consume;
- bloccare token usato, scaduto o con args drift;
- consumare il token prima della prima mutation remota;
- non consumare token per dry-run;
- rendere impossibile trasformare un token dataset-scoped in purge-all.

Preferire il riuso/estrazione di un servizio generico di conferma distruttiva.
Se il vincolo `user_id` di `AdminCommandNonce` impedisce un uso CLI corretto,
aggiungere una persistence dedicata per operazioni demo, con `tenant_id` e
actor espliciti, anziché indebolire il modello esistente.

### 4. Audit della delivery e del purge

Creare un adapter di audit verso `admin_command_audit`.

Per ogni mailbox/tenant coinvolto:

- aprire audit `started` prima del purge/APPEND;
- registrare operazione, dataset version/checksum, mailbox key e conteggi;
- non registrare password, token, host secret o contenuto email;
- completare come `completed` o `failed`;
- registrare tentativi rifiutati per token/env/authorization;
- mantenere il purge-intent tecnico esistente: audit e purge-intent hanno
  responsabilità diverse;
- gestire crash/recovery senza dichiarare due volte un esito terminale falso.

### 5. Preservare l'eccezione R44

Generazione, validazione e delivery del dataset sono tooling operativo
intrinsecamente CLI. Mantenere l'eccezione già documentata:

- nessuna UI per caricare 30.000 email;
- nessun MCP write capace di fare purge/APPEND;
- service layer PHP condiviso testabile;
- motivazione esplicita in ADR, runbook e PR.

Non introdurre endpoint HTTP fittizi soltanto per soddisfare formalmente la
tri-surface.

## Definition of Done

- profilo stress passa con `ulimit -n 256`;
- nessun writer mantiene handle proporzionali al numero di shard;
- ogni purge richiede token DB-backed esatto e single-use;
- ogni mutation remota ha audit durevole e redatto;
- APPEND/purge non possono partire accidentalmente in production;
- hash e determinismo degli artefatti restano invariati;
- pagina Mintlify profonda presente e registrata;
- report di certificazione disponibile o gate dichiarato esplicitamente
  blocked;
- suite completa, critic, Copilot e Playwright finale verdi.
