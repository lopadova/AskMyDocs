## Piano di implementazione

### 1. Estrarre il core delle identity credential

Creare un servizio, ad esempio:

`app/Services/Widget/WidgetIdentityCredentialService.php`

Il servizio deve essere l'unico punto che:

- abilita/disabilita `user_auth_enabled`;
- crea il primo `ik_`;
- ruota `identity_secret_hash`;
- restituisce il plaintext una sola volta;
- applica tenant scope e authorization precondition;
- usa transazioni e row lock per evitare doppie rotazioni concorrenti;
- registra audit durevole senza plaintext o hash;
- espone errori tipizzati per disabled, not found e race.

Il controller deve delegare al servizio. Eliminare la generazione diretta da
`WidgetKeyAdminController`.

Audit minimo per:

- identity auth enabled;
- identity auth disabled;
- identity secret created;
- identity secret rotated;
- tentativo rifiutato.

Usare `admin_command_audit` attraverso un adapter condiviso. Negli argomenti
registrare soltanto widget key id, tenant, project, azione e actor.

### 2. R44 e superfici

Fornire:

- PHP: servizio condiviso e comando Artisan per status/enable/disable/rotate;
- HTTP: mantenere gli endpoint admin come adapter sottili;
- MCP: non restituire un `ik_` plaintext a un agente o nel suo transcript.

Documentare nel codice, nell'ADR e nel PR l'eccezione R44 per la rotazione
segreta via MCP. La motivazione deve essere esplicita: il secret server-to-server
è mostrato una volta e non deve transitare in contesti agentici persistenti.

Se serve una superficie MCP, limitarla a status read-only e metadata non
sensibili; non presentarla come parità della mutation. La mutation resta
deliberatamente PHP + HTTP.

### 3. Correggere il ripristino della sessione

Non far paginare il widget finché trova una sessione aperta.

Creare un contratto server-side esplicito:

- `GET /api/widget/sessions/current`, oppure
- filtro `status=open&per_page=1` sull'endpoint list.

Il server deve:

- filtrare l'identità autenticata;
- includere `active`, `waiting_user`, `waiting_tool`;
- ordinare per `updated_at DESC`, poi id stabile;
- restituire una sola sessione o `204`/payload empty documentato;
- non esporre sessioni di altri utenti/widget/tenant.

Aggiornare `Transport` con `currentSession()` e fare usare quel metodo a
`Bridge.restoreAuthenticatedSession()`.

Test obbligatorio: più di 20 sessioni chiuse recenti e una sessione aperta più
vecchia; la sessione aperta deve essere ripristinata.

### 4. Definire il lifecycle dei token già emessi

Formalizzare e testare:

- disabilitare user auth blocca immediatamente nuove richieste autenticate;
- ruotare `ik_` blocca il minting con il vecchio secret;
- i token utente `wu_` già emessi restano validi fino al TTL oppure vengono
  invalidati tramite un credential epoch.

Scegliere una sola semantica e documentarla. La raccomandazione per rotazione è
preservare i `wu_` fino al TTL, mentre disable deve revocarli immediatamente.
Il validator deve controllare `user_auth_enabled` ad ogni request.

### 5. Stati UI, errori e accessibilità

Verificare panel e admin integration:

- `data-state` e `aria-busy` durante auth bootstrap/history restore;
- composer disabilitato finché l'identità non è pronta;
- errore auth stabile e visibile, non fallback silenzioso a guest;
- fullscreen button con accessible name e stato `aria-pressed`/equivalente;
- focus mantenuto correttamente entrando/uscendo dal fullscreen;
- history empty e failure state distinguibili;
- nessun `waitForTimeout` nei test.

### 6. Playwright real-data

Aggiungere una nuova spec sotto `frontend/e2e/`.

Happy path:

1. creare/configurare una widget key reale con user auth;
2. ottenere un token utente attraverso la boundary prevista;
3. aprire il widget;
4. inviare messaggi reali;
5. ricaricare o riaprire in fullscreen;
6. verificare che venga ripristinata la sessione aperta corretta.

Failure path:

- token identity invalido/scaduto, oppure endpoint host token non valido;
- errore visibile nel DOM e composer bloccato;
- se si intercetta una route interna per failure injection, aggiungere il
  marker R13 e mantenere nello stesso file l'happy path real-data.

Altri scenari:

- utente B non vede la history dell'utente A;
- una sessione aperta oltre la prima pagina viene trovata;
- guest widget continua a funzionare quando user auth non è configurata;
- fullscreen enter/exit non perde session id o messaggi.

## Definition of Done

- nessuna identity credential viene mutata direttamente dal controller;
- ogni mutation è tenant-scoped, atomica e auditata;
- nessun secret compare in audit/log;
- current session funziona indipendentemente dalla paginazione;
- happy e failure E2E real-data sono verdi;
- docs widget, API reference e Mintlify sono allineate;
- tutti i gate locali e CI sono verdi;
- PR con zero must-fix e Playwright finale verde.
